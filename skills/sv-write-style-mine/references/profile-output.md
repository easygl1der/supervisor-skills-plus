This mode turns the Style Profile into research-core files. The method comes
from the owner's archived issue-mining rhetoric skill, whose rules were the
patterns shared by at least four of six exemplar style cards, with a table
for the axes where the cards disagreed. [src: note:n02§8]

## 1. Consensus threshold

- `n` = number of primary cards that passed the readability gate.
- Default `k = max(3, ceil(0.6 * n))`. Examples: n = 5 gives k = 3, n = 6
  gives k = 4 (the archived skill's 4 of 6), n = 10 gives k = 6.
- The user may set another `k`; record it in the profile next to the rules.
- With `n < 3` no rule is produced. Report the observations and ask for more
  exemplars. Five to ten exemplars per venue or field is the target.
- Secondary-corpus and lab exemplars never count toward `k` for a venue
  rule. They may support a field-profile proposal, counted separately and
  labelled.

## 2. From patterns to rule lines

For each pattern row in the Style Profile:

| Support | Goes to |
|---|---|
| `>= k` of n | A rule line (venue profile "Style from exemplars", or a field-profile proposal) |
| `>= 2` and `< k`, and a competing pattern on the same axis also has `>= 2` | "Known disagreements": both positions with their exemplars, and what decides (venue, paper type, length) |
| `>= 2` and `< k`, no competitor | "Unknown": observed in `x/n`, below threshold |
| `1` | Stays on the card; not reported in profiles |

A rule line states the move as an instruction, names its support, and cites
every supporting exemplar by its `lit:` key:

```
- <Instruction stated as a move, no content from the papers> (<x> of <n> exemplars). [src: lit:<key1>; lit:<key2>; lit:<key3>; lit:<key4>] (candidate)
```

Never cite an exemplar that does not show the pattern, and never round up
the support. If the source key list and the support count disagree, fix the
count. Fields K and L of the cards (claims, evidence, threats) produce rules
for "Rigor and threats" and "Tone and phrasing".

Before writing a rule line, search the target profile and the research-core
core files for an existing rule on the same move. If one exists:

- same direction: add the new `lit:` keys to its sources instead of a new
  line;
- opposite direction: record a Known disagreement and do not overwrite the
  existing rule.

## 3. Venue profile (research-core format)

Target: `research-core/references/venues/<venue>.md`, with the headings of
`venues/_template.md` unchanged (Dates, Format, Review model, Required
sections and statements, Desk-reject causes, Submission system, Style from
exemplars, Checklist additions, Changelog).

- **Call sections** (Dates to Submission system): only from the official
  call, fetched now. Quote or closely paraphrase with the URL and fetch date.
  Mark anything ambiguous `CONFIRM`. A remembered or relayed deadline is not
  a source. If the call was not supplied or cannot be fetched, leave the
  template text and write `CONFIRM: call not fetched`.
- **Style from exemplars**: fill it with these sub-parts:

```
## Style from exemplars
Generated by sv-write-style-mine on <date> from n = <n> accepted papers
(<years>, <track>). Threshold k = <k>. Rules are candidates until confirmed.

Exemplars:
1. lit:<key1>: <Authors>. <Title>. <Venue> <year>. DOI <doi>.
2. ...

Structure:
- <rule line>
Contribution format:
- <rule line>
Lengths (measured, ranges only):
- <rule line>
Tone:
- <rule line>
Split axes (below threshold, decided per paper):
- <axis>: <pattern A> (lit:<..>; lit:<..>) vs <pattern B> (lit:<..>; lit:<..>)
```

- **Checklist additions**: only for rules that a reader can check on the
  manuscript. Use the research-core item format with `Scope: venue:<name>`,
  `Status: candidate`, `Owner: sv-write-style-mine, check-loop` (plus others that
  apply), and `Src:` listing the same `lit:` keys. Pick the next free ID with
  the venue's prefix (look up existing IDs first; `check_checklists.py`
  enforces uniqueness).
- **Changelog**: one line, `- <date>: Style from exemplars filled from n = <n> papers (k = <k>).`

## 4. Field-profile proposals

Field rules are proposed, not written directly. Produce
`<style.dynamic_skill>/field-proposals.md`:

```
# Field-profile proposals: <field code> from <venue or corpus> (<date>)
Target file: research-core/references/fields/<field>.md (Version <current>)
Corpus: n = <n> primary (<venue>), m = <m> secondary. Threshold k = <k>.

## Sources (to append)
- lit:<key>: <full reference>

## Typical structure (proposed lines)
- <rule line>
## Tone and phrasing (proposed lines)
## Rigor and threats (proposed lines)
## Checklist additions (proposed items, field code prefix)
## Known disagreements (proposed entries)
## Unknown (proposed entries)

## Duplicates and conflicts found
| Proposed line | Existing line (file:line) | Action (merge sources / disagreement / new) |
```

Only patterns that hold across venues of the field belong in the field
profile. A pattern seen only in one venue's corpus goes to that venue's
profile. If the corpus covers one venue only, say so at the top of the file
and propose field rules only for patterns the existing field profile already
leans toward or leaves Unknown.

## 5. Status and lifecycle

Rules follow the research-core lifecycle (`core/precedence.md`, section 5):

- New exemplar-consensus rules enter as `(candidate)`.
- They become `(confirmed)` when a second, independent corpus or project
  agrees, when the venue call or a published guide states the same rule, or
  when the owner decides (`user:<date>`).
- A later corpus that contradicts a rule produces a Known disagreement first;
  the owner decides whether the old rule becomes
  `(deprecated: <reason>)`.

## 6. Hand-off to lessons-harvest

Writing into research-core goes through `lessons-harvest`: it dedupes
against existing rules, shows the diff, bumps the profile Version and
Changelog, adds a repo CHANGELOG line, and commits on a `learn/<source>`
branch for the owner to merge. When the user asks sv-write-style-mine to write the
venue profile directly, still show the full diff first and leave the merge
to the owner.

## 7. Worked layout (placeholders only)

A six-paper corpus for a conference research track, threshold k = 4:

- "Contribution list" axis: 2 of 6 itemize contributions, 4 of 6 carry them
  through numbered RQs. Result: a rule line for RQ-carried contributions
  (4 of 6) and, because the itemized pattern has 2 supporters, also a Known
  disagreement entry naming both groups.
- "Related work position" axis: 3 early, 3 late. Below threshold on both
  sides: a Known disagreement, decided per paper by the authors and recorded
  in an ADR.
- "Threats organized by four validity categories": 5 of 6. Rule line in the
  venue profile; proposed for the field profile only if the existing profile
  does not already state it (if it does, add the `lit:` keys to its sources).
