# 6.4 一篇实证软工论文的投稿过程 — 过程剖析

> **论文**：一篇关于某个小众软件生态 issue tracker 的实证软件工程研究（已匿名；双盲评审中）
> **会议**：某顶级 SE 会议研究轨
> **原文链接**：暂不公开。本案例剖析的是*过程*，不是正文。录用后再补一篇 6.1–6.3 风格的 Introduction 剖析。

---

## 为什么写一个过程案例

6.1–6.3 讲的是一篇写好的 Introduction 是怎么搭起来的。这一篇讲论文最后几周周围发生了什么：三位作者、几个 AI agent、两份稿子副本、一个微信群、带批注的 PDF，再加一个死线。出问题的地方大多不在写作功底，而在于：证据追不到出处，意见丢了或者被悄悄撤回，需要记录的时候发现没有记录。

下面的内容全部来自项目的 git 历史、聊天导出和 checklist，逐个 commit 核对过。人名、数字和领域细节都已去掉。

---

## 过程 Flowchart

> **冻结数据** → **金标与模型标注** → **撞上数据墙，转进 threats** → **agent 起草初稿** → **外部读者** → **合作者改稿周** → **画图** → **页数与会议规则** → **截稿当天** → **截稿之后**

---

## 逐阶段剖析

| 阶段 | 发生了什么（已泛化） | 导师视角的教训 | 对应 skill |
|---|---|---|---|
| 冻结数据 | 在某个日期冻结语料，按组设下限分层抽样，保证小组也有足够样本。 | 把冻结（日期、总体、筛选规则）写成带备选方案的决策记录；不要悄悄扩充。 | experiment-workflow、research-records |
| 金标与模型标注 | 网页看板显示的进度远少于本地数据库；后来 held-out 参照集有一部分是在看过模型输出后改的，通过线也在同时定下。 | 看板只是视图，可 diff 的文件才是状态。看模型输出之前先冻结评估参照；通过线在跑之前写下来。 | experiment-workflow、research-core 诚信规则 |
| 数据墙 | 相当比例的已关闭 issue 找不到对应修复。补爬几轮都失败后，两位学长一个晚上就拍板：写进 threats to validity，讲清机制，转去做别的 RQ。 | 再爬也补不上的缺口，就把决定连同"不要做什么"清单记下来，然后停止追。这是全项目记录得最好的一个决定。 | feedback-to-revision（指导记录）、research-records |
| agent 起草初稿 | agent 很快把稿子填满，但讲的是研究计划的故事（"计划预测……"），还满是内部黑话。 | 读者评价的是发现，不是是否按计划执行。先回答外行的问题；先讲为什么，再讲怎么做。 | paper-writer、paper-polish |
| 外部读者 | 导师经转述读了稿子，问了一些很基本的问题；七条里有一条针对的文字已经删掉了。 | 记下对方看的是哪一版；指导要连同场景、理解和行动项一起写下来。 | feedback-to-revision（指导记录） |
| 合作者改稿周 | 意见来自 LaTeX 行内批注、PDF 批注、聊天和意见文件。追踪到的约一百条请求里，能核实已改的大约六成。有些只给学生的批注在 agent 的 checkpoint 里消失了；有些被注释掉而不是解决；一次学长基于旧版本的推送悄悄撤回了之前的修改。一份 agent 写的修改报告声称改了十一处，diff 里一处都没有。 | 每条意见编号，一条意见一个 commit，核对 diff 而不是报告，合并后重新核对，绝不隐藏没解决的批注。 | feedback-to-revision |
| 画图 | 方法总览图改了十几版：AI 草图、draw.io 重建、红线标注、手调。合作者参考图上印着的一个统计量被抄进了重建的图，同一个 commit 又写进了方法正文；后来图上删了，正文里还留着。 | 图里的数字和正文的数字一样，必须来自脚本。总览图的框要编号，方法部分一框一步。 | figure-designer、drawio-reconstruction |
| 页数与会议规则 | 表格先挪进附录，后来附录被否决（"没人看，放上去充页数等于直接 reject"）。字体必须保持模板默认；每条参考文献都对照 DBLP 核过。最后关头发现少一页，匆忙补写。 | 删之前先弄清楚什么算进页数。缺页时按优先级补：先给单薄的结果加解释和例子，再写细方法，然后是背景、implications 和 threats。 | pre-submission-reviewer、research-core 会议 profile |
| 截稿当天 | 一周内可写的稿子在 git 和在线编辑器之间换了三次，都没有记录。截稿前二十分钟，自动同步覆盖了一位学长的修改，包括新标题。截稿时投稿网站宕机；几分钟前已经传上去一版 PDF。 | 每个阶段只有一个可写的源头，并且记录下来。同步必须拒绝覆盖。尽早上传一版完整 PDF，之后再替换。 | research-records（sync guard）、pre-submission-reviewer 投稿日清单 |
| 截稿之后 | 前一天的只读检查已经指出复现包的项目主页暴露了作者；三天后才在学长提醒有 desk reject 风险后修好。实际提交的版本始终没有回到仓库里。 | 提前检查发现的阻塞项要立刻处理。截稿后把提交版同步回仓库并打 tag。 | pre-submission-reviewer、research-records |

## 批注

| 位置 | 批注内容 |
|---|---|
| 数据墙 | 整个项目最有用的一份文档是一页笔记：问题是什么、每位学长几点怎么回的、背后的机制、不要做什么。后来所有 threats 段落都是照着它写的。 |
| 改稿周 | 问题不在意见太少，而在渠道太多。解决办法是一张带编号的表，而不是要求大家在聊天里更自律。 |
| 诚信 | 两个严重问题（一个找不到计算记录的一致性数字、一个看过模型输出后修改的参照集）都始于时间压力下的小捷径。"每个数字都有脚本"这条规则本可以同时拦住这两个问题。 |
| Agent | agent 让团队变快，也制造了最大的无声故障：整文件覆盖、批注被删、修改报告没有落地。每次 agent 写完都要看 diffstat。 |
